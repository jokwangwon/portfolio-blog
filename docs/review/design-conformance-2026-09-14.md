# 설계·구현·배포 정합성 검토 — 2026-09-14

## 판단

최신 사용자 결정과 핵심 구조는 대체로 일치한다. 다만 **저장 보호의 예외 경로와 콘텐츠 표현 계약이 미완성**이므로 ‘의도한 설계가 전부 구현됐다’고 판단할 수 없다. 새 기능을 늘리기 전에 아래 P1 두 건을 해결하고 지원할 콘텐츠 형식과 현행 명세를 정리하는 편이 적절하다.

이번 작업은 검토다. 제품 코드·운영 데이터·배포 설정을 수정하지 않았다. 검토용 브라우저 컨텍스트에서만 인증·게시글·저장소 실패를 모의 처리했다.

## 후속 조치 (같은 날)

사용자의 보완 승인 후 P1을 수정했다. 원복 시 중간 복구본을 정리하고, 보관 실패 중 메뉴 이동은 확인하며, SPA 재진입은 탭 내 보조 복원으로 보호한다. 편집기 밖에서도 보조 복구본이 남으면 새로고침 확인을 유지한다. 뒤로/앞으로를 강제로 취소하는 방식은 사용하지 않는다.

아래 발견 사항과 캡처는 **수정 전 근거**다. 최종 구현은 [세션 기록](../sessions/SESSION_2026-09-14.md), [현행 저장 보호 명세](../architecture/blog-ui-design.md), [릴리스 소스 기록](assets/2026-09-14/editor-safety/release.json)을 참조한다. P2/P3 항목은 후속으로 남아 있다.

## 비교 기준과 범위

1. 사용자 결정: 방문자 조회 전용, 관리자 글 관리, 확인된 이력·프로젝트만 소개, 단계별 디자인 및 작성 사용성 개선.
2. public-release-design, portfolio-landing-design의 최신 단계별 적용, blog-ui-design의 글 작성 1차 보완, API 명세, 배포 가이드.
3. 현재 작업 폴더와 직전 운영 이미지의 빌드 사본, 공개 HTTPS의 실제 클라이언트 코드 동작.

최신 보완에서 명시적으로 바꾼 초기 설계는 의도적인 변경으로 분류했다. 예전 100vh Hero·이니셜 이미지·USER 쓰기 권한으로 되돌리는 것이 정합성 개선은 아니다.

## 발견 사항

### P1-1. 원래 내용으로 되돌려도 취소한 수정본이 복구된다

재현: 서버 본문 A → B로 수정 → 브라우저 보관 대기 → A로 다시 변경 → 새로고침 → 복원.

- 새로고침 직전 화면: A.
- 브라우저 복구본: B.
- 복원 후 화면: B.

[PostEditor](../../frontend/src/modules/blog/components/PostEditor.tsx) 55~72행은 현재 값이 baseline과 같아지면 dirty=false로 자동 보관을 끈다.
[useAutoSave](../../frontend/src/modules/blog/hooks/useAutoSave.ts) 62~66행은 disabled 상태에서 기존 복구본을 정리하거나 갱신하지 않는다.
그 결과 사용자가 취소한 수정이 복원 후보로 남는다. 실제 서버 글이 자동으로 바뀌는 것은 아니지만, 복원을 선택하면 의도하지 않은 내용으로 이어 쓸 수 있다.

수정 기준: 원복 상태를 복구본에도 반영하고, 다시 열었을 때 폐기한 중간 내용이 복원되지 않아야 한다. ‘수정→보관→원복→이탈→재진입’을 회귀 테스트에 추가한다.

### P1-2. 브라우저 보관 실패 후 상단 메뉴로 나가면 미저장 내용이 유실된다

재현: 새 브라우저 컨텍스트에서 localStorage.setItem에 QuotaExceededError를 모의 주입 → 본문 수정 → 보관 실패 안내 확인 → 상단 ‘블로그’ 클릭.

- 실패 안내는 표시된다.
- 추가 이탈 확인 없이 /blog로 이동한다.
- 복구본은 null이며 현재 편집 화면이 해제된다.

[PostEditor](../../frontend/src/modules/blog/components/PostEditor.tsx) 210행의 ‘임시저장 목록’ 버튼은 보관 실패 시 확인하지만, 공통 Header의 Next 링크에는 동일한 처리가 없다.
[useAutoSave](../../frontend/src/modules/blog/hooks/useAutoSave.ts) 91~107행의 beforeunload는 브라우저 문서 이탈을 대상으로 하며 일반 SPA 내부 이동의 공통 방어가 아니다. unmount에서는 persist(false)로 실패 알림도 생략된다.

발생 조건은 브라우저 보관 실패와 서버 미저장 상태의 결합이다. 저장소가 정상인 모든 이동이 유실된다는 의미는 아니다.
수정 기준: 저장 실패 중 내부 메뉴·목록·뒤로 이동 정책을 일관되게 적용하고, 이탈 전에 서버 저장·내용 복사·명시적 포기 중 하나를 선택할 수 있어야 한다.

### P2-1. 편집기에서 제공하는 형식과 공개 화면의 지원 범위가 다르다

[RichEditor](../../frontend/src/modules/blog/components/editor/RichEditor.tsx)는 이미지 붙여넣기/드롭을 data URL로 삽입한다.
[MarkdownRenderer](../../frontend/src/modules/blog/components/MarkdownRenderer.tsx) 88~93행은 http/https/상대 경로만 렌더링한다.
고급 블록은 Tiptap NodeView, HTML/마크다운 직렬화, sanitize, 공개 컴포넌트가 각각 다른 책임을 갖지만 지원 표가 없다.

이 문제는 이전 기록에서 후속으로 명시했으므로 이번 1차 작업의 숨겨진 완료 주장으로 취급하지 않는다. 그러나 사용자에게는 이미 선택할 수 있는 기능이므로 ‘지원 기능’과 ‘실험 기능’의 경계를 정할 필요가 있다.
수정 기준: 이미지·표·접기·콜아웃·색상·임베드·수식 각각의 입력/저장/재편집/공개 결과를 규정하고, 지원하지 못하는 기능은 정상 기능처럼 제공하지 않는다. sanitize를 단순히 해제하는 해결은 적절하지 않다.

### P2-2. 요약 생략 시 API 명세와 다른 값이 저장된다

[API 명세](../api/API_SPECIFICATION.md) 402~404행은 마크다운 기호를 제거한 자동 요약을 규정한다.
[PostService](../../backend/module-blog/src/main/java/com/portfolio/module/blog/service/PostService.java) 105~110행 및 152~157행은 원문 substring만 수행한다.
[기존 테스트](../../backend/module-blog/src/test/java/com/portfolio/module/blog/service/PostServiceTest.java) 159~177행은 A 300자의 결과 길이만 검사한다.

예를 들어 본문이 `## 확인 과정`으로 시작하고 요약을 비워 저장하면 요약에도 `##`가 남는다. 새 작성 화면에서 요약이 선택 항목이라 이 경로를 쉽게 사용하게 된다.
수정 기준: 마크다운/HTML을 포함한 본문의 요약 생성 규칙을 정하고 내용까지 검사한다. 생성된 서버 요약과 작성 미리보기의 관계도 명시한다. 이번에는 코드 비교로 확인했으며 운영 DB에 시험 글을 저장하지 않았다.

### P2-3. 배포 소스와 현행 명세를 재현할 기준이 약하다

- 운영 frontend 이미지: `sha256:3ef9eba3e0a7108c6ac67208e5763781976baf7dfe5dc4c24019d4fdb858a673`.
- 문서가 기록한 editor-step1 이미지와 일치한다.
- `/tmp/portfolio-editor-step1-build`와 현재 frontend의 비테스트 파일 238개 비교: 차이는 BlogPreviewSection 1개, 빌드 사본에 없는 비테스트 파일 0개.
- Git 브랜치 `feature/public-release-preparation`, HEAD `15de5e1`. 최근 공개·디자인·작성 개선은 미커밋 상태다.
- [배포 가이드](../guides/DEPLOYMENT_GUIDE.md) 119행의 커밋/이미지 기록 취지에 비춰 현재 HEAD만으로 운영 소스를 재현할 수 없다. 이미지 태그로 되돌릴 수 있는 것과 Git에서 동일 소스를 재빌드하는 것은 별개다.
- [랜딩 명세](../architecture/portfolio-landing-design.md)의 최신 단계와 256행 이후 초기 100vh/placeholder 스펙, [블로그 명세](../architecture/blog-ui-design.md)의 최신 Tiptap 흐름과 초기 Textarea/상태 선택/향후 WYSIWYG 설명이 공존한다.

수정 기준: 현행 요구사항 표를 한 곳에 두고 이전 스펙은 명시적으로 보관 처리한다. 단계별 변경을 Git에 기록하고 릴리스별 커밋·이미지·빌드 옵션·포함/제외 파일을 남긴다. 이번 검토에서는 커밋·배포를 실행하지 않았다.

### P3. 조회 전용 UI 설명에 잔여 불일치가 있다

공개 보완은 좋아요 UI를 숨기도록 하지만 [PostCard](../../frontend/src/modules/blog/components/PostCard.tsx) 54행에는 좋아요 수가 남아 있다.
API 쓰기 차단을 우회하는 문제는 아니며, 읽기 전용 화면의 표현을 정리할 항목이다. 이미 검토한 목록 오류·모바일 긴 태그 문제도 별도 후속으로 유지한다.

## 검증 결과의 해석

- 현재 frontend 25개 테스트 파일, **146 tests 통과**.
- 문서 링크 검사 171개, 깨진 링크 0(보고서 추가 전).
- 공개 코드에서 위 두 저장 예외를 브라우저로 재현했다. 실제 관리자 정보·운영 게시글을 사용하거나 수정하지 않았다.
- 테스트 통과와 문서 링크 정상이 의미적 설계 일치까지 증명하지는 않는다. 이번 재현은 기존 테스트의 검증 범위 밖이었다.
- 이전 단계의 전체 백엔드 147 tests와 DB 복원/HTTPS 기록은 참고했지만 오늘 다시 실행하지 않았다.
- 최신 작성 화면→실제 서버→DB→재조회 전체 흐름은 아직 모의 응답 검증과 분리해 남아 있다. 이번 검토의 목적상 실데이터 쓰기를 추가하지 않았다.
- 커버리지 70% 목표 충족 여부는 이번 테스트 실행만으로 확인하지 않았다.
