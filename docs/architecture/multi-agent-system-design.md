# 멀티 에이전트 시스템 설계

> **검토 에이전트 1 + 개발/분석 에이전트 3 — 합의 기반 의사결정 시스템**

**최종 수정**: 2026-03-30
**상태**: 설계 완료 (Phase 1 적용)
**관련 ADR**: 신규 (ADR-007 후보)

---

## 1. 개요

### 1.1 목적

코드 개발, 문서 검토, 기술적 질문 분석 시 **단일 에이전트의 편향**을 제거하고 **다관점 합의**를 통해 최선의 결정을 도출하는 시스템.

### 1.2 핵심 원칙

1. **독립 분석**: 각 에이전트는 독립적으로 분석 후 결론 도출
2. **교차 비교**: 에이전트 간 출력을 비교하여 일치/불일치 식별
3. **합의 도출**: 검토 에이전트가 최종 판단을 종합하여 최선의 방향 제시
4. **투명성**: 모든 에이전트의 의견과 근거가 사용자에게 공개됨

## 2. 시스템 아키텍처

### 2.1 에이전트 구성

```
┌─────────────────────────────────────────────────┐
│                   사용자 요청                      │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────┐
│            🔍 검토 에이전트 (Reviewer)              │
│                                                   │
│  역할: 작업 분배, 출력 비교, 최종 합의 도출            │
│  입력: 사용자 요청 + 3개 에이전트 출력                 │
│  출력: 최종 판단 보고서                              │
└───┬──────────────┬──────────────┬───────────────┘
    │              │              │
    ▼              ▼              ▼
┌────────┐  ┌────────┐  ┌────────┐
│ Agent A │  │ Agent B │  │ Agent C │
│ (분석1) │  │ (분석2) │  │ (분석3) │
│         │  │         │  │         │
│ 관점:   │  │ 관점:   │  │ 관점:   │
│ 구현    │  │ 품질    │  │ 대안    │
│ 가능성  │  │ /안전성 │  │ 탐색    │
└────────┘  └────────┘  └────────┘
```

### 2.2 에이전트 역할 정의

#### 검토 에이전트 (Reviewer Agent)

| 항목 | 설명 |
|------|------|
| **역할** | 관제탑 — 작업 분배, 결과 종합, 최종 판단 |
| **입력** | 사용자 요청 원문 + Agent A/B/C 출력 전체 |
| **처리** | 3개 출력 교차 비교 → 일치/불일치/누락 분류 → 최선 방향 도출 |
| **출력** | 합의 보고서 (판단, 근거, 위험도, 권장 행동) |
| **권한** | 최종 의사결정권 — 에이전트 간 의견이 갈릴 때 판정 |

#### Agent A — 구현 분석가 (Implementation Analyst)

| 항목 | 설명 |
|------|------|
| **관점** | "이것이 실제로 동작하는가?" |
| **초점** | 기술적 구현 가능성, 코드 수준 실현 방법, 의존성 분석 |
| **질문 예시** | 이 설계를 Spring Boot로 어떻게 구현하는가? 성능 병목은? |
| **강점** | 구체적 코드 레벨 분석, 기술 스택 호환성 검증 |

#### Agent B — 품질/안전성 검증가 (Quality & Safety Auditor)

| 항목 | 설명 |
|------|------|
| **관점** | "이것이 안전하고 견고한가?" |
| **초점** | 보안 취약점, 엣지 케이스, 테스트 커버리지, 문서 정합성 |
| **질문 예시** | SQL Injection 가능성은? 인증 우회 경로는? 문서와 코드가 일치하는가? |
| **강점** | 방어적 관점, SDD 명세 대비 편차 탐지 |

#### Agent C — 대안 탐색가 (Alternative Explorer)

| 항목 | 설명 |
|------|------|
| **관점** | "더 나은 방법이 있는가?" |
| **초점** | 대안 기술, 다른 설계 패턴, 트레이드오프 비교 |
| **질문 예시** | 다른 아키텍처 패턴은? 이 라이브러리 대신 무엇이 가능한가? |
| **강점** | 시야 확장, 기존 결정에 대한 건전한 도전 |

## 3. 실행 프로토콜

### 3.1 워크플로우

```
Phase 1: 분배 (Distribution)
─────────────────────────────
검토 에이전트가 사용자 요청을 분석하고
각 에이전트에게 관점별 분석 지시를 전달

Phase 2: 독립 분석 (Independent Analysis)
─────────────────────────────────────────
Agent A, B, C가 동시(병렬)로 독립 분석 수행
서로의 출력을 참조하지 않음 (편향 방지)

Phase 3: 교차 비교 (Cross-Comparison)
─────────────────────────────────────
검토 에이전트가 3개 출력을 수집하여:
 ① 일치점 (Consensus) — 3개 모두 동의
 ② 부분 일치 (Partial) — 2개 동의, 1개 이견
 ③ 불일치 (Divergence) — 3개 모두 다른 의견
 ④ 누락 (Gap) — 특정 에이전트만 언급한 사항

Phase 4: 합의 도출 (Consensus Resolution)
─────────────────────────────────────────
검토 에이전트가 최종 판단:
 - 일치: 그대로 채택
 - 부분 일치: 소수 의견의 근거 평가 후 결정
 - 불일치: 각 근거를 비교하여 최선 선택 + 이유 명시
 - 누락: 해당 사항의 중요도 평가 후 포함/제외 결정

Phase 5: 보고 (Report)
──────────────────────
사용자에게 최종 합의 보고서 전달
```

### 3.2 출력 형식

#### 개별 에이전트 출력 (Agent A/B/C)

```markdown
## [Agent X] 분석 결과

### 관점: {구현 분석 / 품질 검증 / 대안 탐색}

### 핵심 판단
{한 줄 요약}

### 상세 분석
1. {분석 항목 1} — {결론} — {근거}
2. {분석 항목 2} — {결론} — {근거}
...

### 위험 요소
- [CRITICAL] {설명}
- [WARNING] {설명}

### 권장 사항
- {구체적 행동 1}
- {구체적 행동 2}
```

#### 검토 에이전트 합의 보고서

```markdown
## 🔍 합의 보고서

### 요청 요약
{사용자 요청 한 줄 요약}

### 교차 비교 결과
| # | 항목 | Agent A | Agent B | Agent C | 합의 |
|---|------|---------|---------|---------|------|
| 1 | ... | ✅ 동의 | ✅ 동의 | ✅ 동의 | ✅ 채택 |
| 2 | ... | ✅ 동의 | ⚠️ 조건부 | ❌ 반대 | ⚠️ A안 채택 (근거: ...) |
| 3 | ... | — | ✅ 제기 | — | ✅ 추가 채택 |

### 최종 판단
{합의된 최선의 방향 상세 설명}

### 채택하지 않은 의견 (참고용)
- Agent C의 대안: {내용} — 미채택 이유: {근거}

### 위험도 평가
| 등급 | 항목 | 대응 |
|------|------|------|
| CRITICAL | ... | 즉시 조치 |
| WARNING | ... | 모니터링 |
| INFO | ... | 참고 |

### 권장 행동
1. {최우선 행동}
2. {차선 행동}
```

## 4. 적용 시나리오

### 4.1 코드 개발 시

```
사용자: "Auth API 구현해줘"

검토 에이전트 → 분배:
  Agent A: JWT + SecurityFilterChain 구현 코드 분석
  Agent B: OWASP 보안 체크, SDD 명세 대비 검증
  Agent C: Session vs JWT vs OAuth2 트레이드오프

검토 에이전트 → 합의:
  "JWT HS256 구현 (SDD 명세 준수), Agent B가 지적한
   Rate Limiting 추가 권장, Agent C의 OAuth2는 Phase 2로 연기"
```

### 4.2 문서 검토 시

```
사용자: "SDD 명세 완전성 분석해줘"

검토 에이전트 → 분배:
  Agent A: DB 스키마 + Migration 실행 가능성
  Agent B: API 명세 ↔ openapi.yaml 정합성, 보안 명세
  Agent C: 아키텍처 일관성, 누락된 설계 항목

검토 에이전트 → 합의:
  "18개 CRITICAL 이슈 발견 — 4 Phase 보완 계획 수립"
```

### 4.3 기술적 질문/의사결정 시

```
사용자: "PostgreSQL vs MongoDB 어떤 게 나은가?"

검토 에이전트 → 분배:
  Agent A: 현재 스키마 기준 PostgreSQL 구현 분석
  Agent B: 데이터 무결성, 트랜잭션, 보안 비교
  Agent C: MongoDB 마이그레이션 비용, 유연성 분석

검토 에이전트 → 합의:
  "PostgreSQL 유지 (3:0 합의) — 관계형 데이터 모델,
   ACID 트랜잭션, 기존 Flyway 투자 보존"
```

## 5. 구현 가이드

### 5.1 Claude Code에서의 실행 방법

```
# 검토 에이전트 역할: 메인 컨텍스트 (Claude Code 자체)
# Agent A/B/C: Agent 도구를 사용한 서브에이전트

1. 메인 컨텍스트가 요청을 분석하고 3개 Agent 도구를 병렬 호출
2. 각 Agent에게 역할(관점)과 분석 대상을 명시적으로 지시
3. 3개 출력을 수집한 후 메인 컨텍스트가 교차 비교 수행
4. 합의 보고서를 사용자에게 제출
```

### 5.2 에이전트 호출 예시 (의사 코드)

```python
# Phase 2: 병렬 독립 분석
agent_a = Agent(
    role="구현 분석가",
    prompt=f"""
    관점: 기술적 구현 가능성
    분석 대상: {user_request}
    참조 문서: {relevant_docs}
    출력 형식: 핵심 판단 → 상세 분석 → 위험 요소 → 권장 사항
    """
)

agent_b = Agent(
    role="품질/안전성 검증가",
    prompt=f"""
    관점: 보안, 품질, SDD 정합성
    분석 대상: {user_request}
    참조 문서: {relevant_docs}
    출력 형식: 핵심 판단 → 상세 분석 → 위험 요소 → 권장 사항
    """
)

agent_c = Agent(
    role="대안 탐색가",
    prompt=f"""
    관점: 대안 기술, 트레이드오프
    분석 대상: {user_request}
    참조 문서: {relevant_docs}
    출력 형식: 핵심 판단 → 상세 분석 → 위험 요소 → 권장 사항
    """
)

# Phase 2: 병렬 실행
results = parallel_execute(agent_a, agent_b, agent_c)

# Phase 3-4: 검토 에이전트가 교차 비교 및 합의 도출
consensus = reviewer.compare_and_resolve(results)

# Phase 5: 보고
return consensus.report()
```

### 5.3 적용 기준

모든 요청에 3-에이전트 시스템을 사용하면 비효율적이므로, 다음 기준으로 적용:

| 요청 유형 | 에이전트 수 | 이유 |
|-----------|------------|------|
| 단순 코드 수정/버그 fix | 1 (직접 처리) | 오버헤드 불필요 |
| API/기능 구현 | 1~3 (복잡도에 따라) | 중간 규모는 2개로 축소 가능 |
| 아키텍처 의사결정 | 3 (필수) | 다관점 필수 |
| SDD 명세 검토 | 3 (필수) | 교차 검증 필수 |
| 보안 관련 변경 | 3 (필수) | 보안은 다중 검증 필수 |

## 6. 품질 보증

### 6.1 에이전트 간 품질 메트릭

| 메트릭 | 측정 방법 | 목표 |
|--------|----------|------|
| 합의율 | 3개 모두 동의한 항목 비율 | > 60% |
| 유효 이견 비율 | 소수 의견이 채택된 비율 | > 10% |
| 누락 탐지율 | 1개 에이전트만 발견한 CRITICAL 이슈 비율 | 추적 |

### 6.2 피드백 루프

```
합의 보고서 → 사용자 확인 → 수정 요청 시:
  ① 어떤 에이전트의 판단이 틀렸는지 기록
  ② 해당 관점의 프롬프트 개선
  ③ 다음 호출에 반영
```
